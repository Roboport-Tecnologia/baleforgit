# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Prime directives

- data corruption is not allowed ever
- data races are not allowed ever
- race conditions are not allowed ever
- every feature or implementation plan should take into account data corruption and race risks
- after every feature implemented the code should be audited for data corruption and race risks
- this is not a v1, this is production, no data loss ever

## Start here

- **`docs/ARCHITECTURE.md`** — read this before making non-trivial changes. It covers the three pluggable traits (`BlobStore`, `MetadataStore`, `RepoAuthz`), upload/download/global-dedup flows, the wire surface, storage layout, auth flow, the native `git-bale` filter, the OpenTelemetry observability story (gated on `OTEL_EXPORTER_OTLP_ENDPOINT`), and a "Tricky bits" section calling out the parts of the Bale protocol that are easy to get wrong (hex encoding, `url_range` end-inclusivity, signed-URL Range matching, idempotency, shard magic tag).
- **`docs/BALE_FORGE_PROTOCOL.md`** — the contract a git forge has to implement to support `git-bale`: an HTTPS `/info/bale/authenticate` endpoint, an SSH `git-bale-authenticate` command, and a `POST /check_access` callback consumed by `bale-server-authz-http`. Read before touching the `git-bale` auth resolver or `HttpAuthz`.
- **Scope** — the server (CAS upload/download/global-dedup endpoints, HS256 token auth), the native `git-bale` filter, alternate trait impls, the per-repo scope check on reconstruction, and per-owner + per-repo storage accounting + quotas (the `/v1/usage/{owner}`, `/v1/usage/repo/{owner}/{repo}`, and `/v1/quotas/{owner}` endpoints) are all implemented. See `docs/STATUS.md`.
- **`crates/git-bale/`** — native Git filter (`filter.bale.process`). Pretty-printed JSON pointer with stable key order (`hash`, `file_size`, `sha256`), shared chunk cache (`~/.cache/bale/chunks` by default), per-repo manifest cache (`.git/bale/manifests/`), and a per-repo **pointer cache** (`.git/bale/clean-cache/<blake3>`) that short-circuits `clean` when the same input bytes have been cleaned before (each entry records the canonical object store it was written to plus that store's random `.bale-id` (created at claim/register, carried through prune's swap — except after `--force` skipped a repo, whose un-retired clean-cache must then miss), and a hit is honored only against that same store — after `init-local --store` switches stores, or a store wiped and re-created at the same path (new id), a hit would emit a pointer whose bytes the current store lacks; `local-store-switch`) — `git status` / `git diff` on a modified bale file would otherwise re-run full CDC + xorb + shard work on every command. **Clean is offline: `git add` chunks the file via `TranslatorConfig::local_config` and writes xorbs/shards to `.git/bale/staging/` instead of POSTing to the server.** `git-bale push-pending` uploads ONLY bale files reachable from the pushed ref delta, plus staged content the TARGET already references (reachable from the stdin remote shas or `refs/remotes/<target>/*` — commits pushed earlier with `--no-verify` would otherwise advertise bytes that exist only locally; tested only for markers the delta didn't cover, with want-set early exit) (markers from `git status`/`git diff` re-cleans of uncommitted edits stay local and staged for gc; draining removes only uploaded markers; run by hand with no args it treats HEAD as the push and uploads only staged content HEAD reaches). It ensures every bale file the push *advertises* reaches — and is registered under — the repo of the remote being pushed to: it does NOT POST staged xorbs/shards verbatim (that bypasses server global dedup), it reconstructs each file to a temp and re-cleans it through an online `FileUploadSession` pointed at the target (xet POSTs only new xorbs but always its per-session shard, and that `/shards` POST is what makes the server `register_files(<target repo>, …)`). Two file classes: **freshly staged** files (sourced from `.git/bale/staging/`) and **already-pushed-elsewhere** files reachable from the pushed ref delta but drained from staging by an earlier push to a *different* remote (discovered via the same gix rev-walk gc uses, bounded only by the stdin remote shas — NOT by `refs/remotes/<target>/*`, since git refs on a remote don't imply the bale objects were registered there; that false assumption is what broke pushing to a remote already holding the history. Each candidate is probed via `GET /v1/reconstructions/{hash}` with the target token and skipped if already registered; bytes for the rest are re-sourced from whichever remote still holds them — `origin` first — via a read-scoped reconstruct). Auth is minted against the **push target** (`resolver::resolve_for_remote`, fed the pre-push hook's `$2` URL), not `origin`, so an upload lands in the right server-side repo scope — this is what makes multi-remote (two repos on one server) work; without it a clone of the second remote 404s on checkout (`multi-remote` e2e phase). The pre-push hook installed by `git-bale install --local` runs `git-bale push-pending "$@"` (remote name + URL as `$1`/`$2`, ref updates on stdin) before `git push`; run by hand with no args it falls back to `origin` and drains only staging. If no remote can reconstruct an already-committed file, the push fails rather than advertise an unreconstructable pointer. **All `.git/bale/` bookkeeping (staging, markers, clean-cache, manifests, default local store) keys on the COMMON git dir (`store::common_git_dir`), so linked worktrees share one inventory (no backward compatibility with older layouts — nobody uses this yet). Clean only ever *adds* to staging; the objects are the only copy until pushed and xet doesn't fsync them, so clean fsyncs the newly created xorbs/shards (`store::ObjectSnapshot`, diffing dir listings) and their dirs BEFORE writing the marker — and for every new shard, validates (`XorbObject::validate_xorb_object`) and fsyncs every xorb its files reference, failing the clean if one is missing/corrupt (a dedup hit can land on an older xorb a power loss tore), and markers / clean-cache / manifests / registry entries are written tmp → fsync → rename → fsync dir (`fs_util::write_durable`); a failed marker write fails the clean; `git-bale gc` (`gc.rs`) reconciles it with git-gc liveness: a marker is live if its pointer is reachable from ANY ref (local or remote-tracking), ANY reflog entry (`stash@{n}`, reset-away commits), any worktree's HEAD/pseudo-refs, any stopped rebase/merge state (`rebase-merge/autostash`, `rebase-apply/autostash`, `MERGE_AUTOSTASH`, `rebase-merge/{orig-head,onto,stopped-sha,amend}`, `sequencer/{head,abort-safety}` — a conflicted `rebase --autostash` holds the user's uncommitted changes ONLY there), or any worktree's index (`rev_walk(...).all()`, nothing hidden, diffing each commit against its first parent). A stopped rebase/am/sequencer/autostash merge also counts as "op in flight", so gc skips entirely. Remote-tracking reachability is NOT proof of upload (`push --no-verify`, plain-git remotes) — in server mode only push-pending's post-upload drain releases committed staged content. Every liveness error (unreadable index/ref/reflog, walk/diff failure, missing object, config load) aborts gc keeping everything, and `git-bale gc` then prints a one-line `warning: git-bale gc refused…` to stderr and exits 1 (the hooks' `|| true` would otherwise hide it). gc only scans markers OLDER than the reclaim grace (young ones are kept anyway), so the full-history walk doesn't run on every hook. Partial clones (`extensions.partialClone`, `remote.*.promisor`, `*.promisor` packs): gc quietly reclaims nothing (debug log), prune refuses; push-pending collects blobs missing locally, fetches exactly those via `git cat-file --batch-check` (lazy promisor fetch), retries once, and only then fails with an explicit partial-clone message. push-pending's final object sweep is skipped while a git op is in flight. Objects are swept only once no marker remains (deduped across files), and the sweep renames the whole `<store>/xet` dir (xorbs, shards, redb dedup index) aside before deleting it, so a crash can't leave the dedup index pointing at deleted xorbs. gc invalidates the clean-cache entries of every hash it drops (`clean_cache::forget_hashes`, before removing markers) so a later re-`git add` does a full clean + re-stage instead of short-circuiting to a pointer with no retrievable backing — without this, `git add` → `restore --staged` (fires post-checkout gc) → re-add → `git stash`/`pop` lost the staged bytes. Without gc at all, a `git add` you then abandon via `git reset`/`git checkout` would leak staged bytes forever and even get uploaded on the next push.** `install --local` also writes `post-checkout`/`post-commit`/`post-merge` hooks that run `git-bale gc || true` (best-effort: a foreign hook of that name is skipped, not clobbered, unlike the correctness-critical pre-push which errors). Driven end-to-end by the `gc-abandon-checkout`/`gc-keeps-unpushed`/`gc-mixed` phases in `tests/e2e/run.py`. Smudge order: hot path (manifest + chunk cache) → lukewarm path (reconstruct from `.git/bale/staging/` if not yet pushed) → cold path (`/v1/reconstructions/`). **Every path verifies the assembled bytes against the pointer's size + sha256 before `status=success`** (xet doesn't re-hash chunks): hot/lukewarm mismatches fall through, a cold mismatch retries once without the chunk cache then fails, a local-store mismatch fails; bad bytes never reach the worktree or the clean-cache. The payload is always drained to its flush before replying, non-pointer smudge input passes through unchanged (like git-lfs), and clean input that already IS a canonical pointer (byte-identical to what git-bale writes, with `file_size` + `sha256`; a user JSON that merely has a `"hash"` key is cleaned normally) passes through unchanged too (a worktree checked out before the filter was installed would otherwise be committed as a pointer-to-a-pointer — `local-pointer-passthrough`); a pointer without `sha256` is refused on every smudge path (unverifiable), and a read error mid-content uses git's flush-then-`status=error` form. The cold path is wrapped in a **no-progress watchdog** (`download_cold` in `filter_process.rs`, shared with `git-bale mount`): it counts bytes actually written and aborts with a user-facing error if none arrive for `BALE_DOWNLOAD_STALL_SECS` (default 30s; `0` disables). This exists because reconstruction bytes are fetched by the *client* directly from presigned blob-store URLs, so a blob store reachable by the server but not the client (e.g. a bundled MinIO presigned as the compose-internal `minio:9000`) fails only here — and xet-core's retry layer misclassifies the "host not found" DNS error as retryable, then `ExponentialBackoff::from_millis(3000)` (tokio-retry squares each step) parks the 2nd retry for up to ~2.5h, hanging `git checkout` silently for hours without the watchdog. Auto-resolves `server_url` + token from `origin` via the forge protocol (HTTPS Basic via `git credential fill`, or SSH `git-bale-authenticate`); a **read/download** resolve over HTTPS tries the forge anonymously first and only falls back to `git credential fill` on 401/403, so cloning a **public** repo never prompts (`authenticate_http_with_fallback` in `resolver.rs`, exercised by the `anon-public-clone` e2e phase). Uses `bale.serverUrl` + `bale.token` (env `BALE_SERVER_URL`/`BALE_TOKEN`, else git config at any scope) only when BOTH are set; half a pair is ignored with a warning (a lone token must never reach a forge-discovered server). Remote user/host starting with `-`, containing whitespace/control chars, or `@` in host are rejected, and ssh gets `--` before the destination. A cleartext `http://` forge href or `casUrl` is refused for an https/ssh remote unless the host is loopback (`resolver::require_tls`). Path canonicalization uses `dunce` so Windows never sees `\\?\` verbatim paths (subprocess cwds, messages). Depends on `xet-data`, `xet-client`, `xet-core-structures`, `xet-runtime` from crates.io, pinned to `=1.5.2`. Uses `gix` for pure-Rust git ops: rev-parse, tree diff, ODB blob reads, `gix::discover` + config snapshot in `config.rs`, `find_remote("origin")` + `remote_names()` (push-pending's multi-remote re-sourcing) in `remote.rs`, and `common_dir().join("hooks")` (or `core.hooksPath` resolved like git: `~` expanded via `trusted_path`, relative to the worktree root) in `install.rs`; a global/system `install` writes no hooks and warns that `install --local` is required per repo. Things still shelling out: `git credential fill` and SSH in `resolver.rs` (forge auth — no library equivalent), and `git config --local/--global/--system` writes in `install.rs` (one-time setup, gix's typed-key write API is more complex than the subprocess for arbitrary user keys). The SSH `git-bale-authenticate` subprocess honors git's own ssh-command config — `GIT_SSH_COMMAND` env, else `core.sshCommand` (same precedence git uses), threaded through `RawConfig.ssh_command` into `ssh_subprocess` which runs a configured command via `/bin/sh` with the auth args appended (bare `ssh` when unset). This matters beyond convenience: ssh expands `~` for its default `UserKnownHostsFile` via `getpwuid`, *not* `$HOME`, so a bare `ssh` would write the server's host keys into the developer's real `~/.ssh/known_hosts` even under the e2e harness's isolated `$HOME` — honoring the harness's `GIT_SSH_COMMAND` (which pins `UserKnownHostsFile`) keeps the handshake from polluting it. The `xet-core/` sibling clone is present only as a source reference for Claude — it's not in the build graph, and the root `Cargo.toml` `exclude`s it so cargo doesn't try to descend into its workspace. **Fully-local (no-server) mode:** `git-bale init-local [--store <path>] [--shared]` sets `bale.local=true` (+ `bale.localStore` only for a non-default store: the per-repo default is derived from the current git dir so a moved repo follows it) in local git config; only init-local creates a store — clean/smudge/gc/prune refuse a store path with neither `.bale-owner` nor `repos/` (moved repo, unmounted disk) instead of silently starting an empty one there (`local-moved-repo`), installs gc hooks, and (with `--shared`) sets `bale.localShared=true` and registers the repo in `<store>/repos/`; it does NOT install the pre-push hook (nothing to drain). Config keys: `bale.local`/`BALE_LOCAL` (bool), `bale.localStore`/`BALE_LOCAL_STORE` (path, tilde-expanded), `bale.localShared`/`BALE_LOCAL_SHARED` (bool). `crate::store::object_store_root` returns staging in server mode; in local mode it returns the configured store (default per-repo `.git/bale/store`, or `~/bale-local` with `--shared`). Per-repo bookkeeping — `file-index/` markers, clean-cache, manifests — always stays under `.git/bale/` even when the object store is shared. Smudge: hot → store-only reconstruct → **hard error** (no staging path, no network, no auth). `push-pending` is a no-op in local mode. gc liveness is the same as server mode; on shared stores gc is append-only — `git-bale prune --shared` reclaims by rebuilding the store. Prune liveness is gc's liveness (refs, reflogs, indexes, HEADs, rebase state) unioned over every PRESENT registered repo, plus young markers — never "which repo holds a marker" (content cleaned by B may be referenced only by A, and B may be gone; `--force` skips a missing repo, deleting content ONLY it referenced; clean and gc re-register a shared repo under its current path on every run (`store::register_repo_locked`), so a moved/copied repo stays live after its next clean/gc); the store's own shards (`MDBShardFile::read_all_file_info_sections`) say which files it holds and their sizes; the compacted store is fsynced before the swap and the parent dir after, it waits (without holding the lock) until no registered repo has a git `*.lock`, retires dead markers + clean-cache entries in every repo BEFORE the swap, and aborts on missing repos unless `--force`. A NON-shared local store belongs to one repo: `store::claim_store` records the owner's common git dir in `<store>/.bale-owner` (init-local / first clean); init-local, clean and gc refuse a non-shared store owned by another repo (or one registered as shared), and gc never sweeps a store it doesn't own — two repos pointed at one non-shared store would otherwise have one's gc wipe the other's content. `.bale-owner` is authoritative even for a store inside the repo's own git dir (it records the sentinel `@containing-git-dir` when the store is under `<common>/bale/` — not merely under `<common>`, which also holds submodules' git dirs — so moves/copies keep the claim, but a foreign repo `--store`d into another's git dir is refused, in either claim order — `local-in-gitdir-store-claim`). In local mode "zero markers" ≠ "nothing live" (a repo re-cloned at the same path re-claims its store with no markers; the store is the only copy), so gc's whole-store sweep first reads the store's file set from its shards and sweeps only if none is reachable (`gc::sweep_store`, `local-reclone-same-path`). If a crash interrupts the swap (store path missing, `<store>.old.*`/`.compact.*` present), `store::object_store_root` makes clean/smudge/gc/prune refuse instead of recreating an empty store. prune also refuses to start while any `.old.*`/`.compact.*` leftover exists, so a later crash can't leave several backups to choose between. Store paths are canonicalized before deriving the lockfile; `register_repo` takes the lock. **Store lock (`crate::store::StoreLock`, fs4 advisory `flock`/`LockFileEx`):** every store *mutator* takes one exclusive lock on a sibling lockfile `<store-parent>/.<storename>.lock` (outside the dir so prune's rename can't move it) — `clean` BRIEFLY **per file** across {write objects → write marker} (the cache-hit path only to touch the marker; in local mode a hit with no marker falls through to a full clean) (NOT the filter-process lifetime: a long hold deadlocks when a git porcelain op like `stash`/`commit -a` nests another clean while the outer filter holds the lock — hung the `offline-no-network` phase), `gc` via non-blocking `try_exclusive`, `push-pending`/`prune` across their sweeps/run. Reads (smudge) never block on it (seeding the clean-cache after a smudge takes it only via `try_exclusive` and skips on contention, and seeds in local mode only when the bytes came from the store itself, not a hot-path hit); different stores never contend; OS releases on crash. This closes the object-vs-marker window. The separate **marker-vs-index** window (git updates its on-disk index *after* the filter returns, so a marker can exist before git references it; a racing gc would read the stale index and sweep the new file's only copy) is closed by **gc deferring while any git index/ref `*.lock` exists in ANY worktree** (`gc::git_op_in_flight`: `index.lock` for add/commit, `index.<temp>.lock`+`refs/stash.lock` for stash — stash uses a temp index so the main `index.lock` is absent; checked *after* the store lock so a clean can't slip in between; an unreadable dir counts as in flight). The one lock-free residual (a `git stash`'s commit-write between its temp-index unlock and `refs/stash.lock`) is closed by a **reclaim grace**: gc won't drop/sweep a marker whose content was cleaned within `BALE_GC_GRACE_SECS` (default 2 weeks — git's `gc.pruneExpire`, so a dropped stash stays recoverable with its bytes as long as git keeps the commit); clean rewrites the marker mtime on every add (hit included, under the lock) so "marker age" == "time since cleaned". Trade-off: abandoned content lingers up to the grace before reclaim. Tested by `local-gc-grace` (young orphan survives gc, reclaims once aged); the harness sets `BALE_GC_GRACE_SECS=0` elsewhere so the abandon/race phases test the lock + in-flight check directly. `push-pending`'s drain is surgical under the lock (remove only uploaded markers; sweep objects only if none remain) so a concurrent add isn't blanket-deleted. Driven by `local-basic`/`local-gc-abandon`/`local-shared-dedup`/`local-prune-shared`/`local-stash-reflog`/`local-worktree-gc`/`local-prune-cross-repo`/`local-tampered-store`/`local-autostash`/`local-prune-missing-repo`/`local-store-owner`/`local-moved-shared-repo`/`local-reclone-same-path`/`local-in-gitdir-store-claim`/`local-pointer-passthrough`/`local-moved-repo`/`local-store-switch`/`local-prune-force-moved` plus `local-clean-gc-race` + `local-cache-hit-gc-race` (deterministic data-loss races via `BALE_TEST_CLEAN_MARKER_DELAY_MS` / `BALE_TEST_CLEAN_CACHE_HIT_DELAY_MS`) and `local-concurrent-stress` (natural-timing add/gc/prune contention, also a deadlock check) in `tests/e2e/baleharness/phases/local.py` (g3 group, no server).
- **`tests/e2e/`** — out-of-band full end-to-end harness (`tests/e2e/run.py`) that bundles `baleforgit-server` + `openssh-server` in one podman container and drives the release `git-bale` binary through stage/unstage/stash/pop/commit/push/clone over real SSH (including the `multi-remote` phase: push to one repo, then to a second repo on the same server and clone it; plus a third repo seeded with the git commits but no bale objects — via a neutered hook — to which a new branch is pushed and cloned, proving push-pending registers under the push target's scope even when the target already holds the history). Includes a 35 MB binary with two slight modifications so chunk-level dedup is verifiable against on-disk numbers AND the `/v1/usage/...` API, plus adversarial cases (wrong token, tampered xorb on disk, quota exceeded, `upload-guards`: direct-HTTP negative tests of the server's upload-time `verify_xorb_body` integrity gate, the signed transfer-URL guards (forged/expired/Range-mismatch), and write-scope enforcement; `shard-guards`: shard proof-of-possession (replayed terms without valid verification hashes can't register a file into another repo), dedup-index poisoning via client CAS blocks, LZ4 decompression bomb, two-encoding xorb races; `xorb-layout-heal`: a failed blob write must not pin its frame layout over a differently-compressed later upload; `global-dedup-hit`: a fresh-cache second user pushing stored content dedups against the server (zero xorb uploads) and passes shard verification; `oversize-xorb`: a legit xorb serializing over 64 MiB uploads; `large-file`: a 600 MiB cold clone, which xet fetches in Range blocks; `fetch-overlap` / `dedup-repeated-chunk`: files whose terms overlap within one xorb, and a xorb that repeats a chunk, crafted with the `bale-e2e-tools` helper; `quota-atomic`: concurrent shards can't jointly overshoot a quota, and unreferenced uploads are charged to the uploader; `canonical-scope`: the forge's canonical scope key + accounting owner win over the typed repo name and survive a transfer). The **whole** suite also runs against an S3 (MinIO) blob store via `tests/e2e/run.py --backend s3`: a process-global backend (`baleharness/s3backend.py`, mirroring the coverage-mode global) makes `start_container` bring up a per-run MinIO sidecar + network and auto-inject `BALE_S3_*` for every container, each server scoped to its own bucket prefix derived from its `data_root`; `ServerHandle.disk_*_bytes()` answers from `mc ls` so the storage-accounting assertions work unchanged, and `tampered-xorb` corrupts bucket objects instead of on-disk files. The one S3-only scenario — a server↔MinIO connection drop mid-PUT (via a host-side TcpProxy) — is the `failure-s3-conndrop` phase, which self-skips under the fs backend. A small `tests/e2e/s3lib.py` survives with two phases (`phase_s3_basic`, `phase_s3_dedup`) that `--coverage` runs against the instrumented image so `bale-server-storage-s3` shows up in the report; it has no standalone entry point. The **whole** suite likewise runs against a **Postgres `MetadataStore`** via `tests/e2e/run.py --meta postgres`: `baleharness/pgbackend.py` (mirroring `s3backend.py`) brings up a per-run Postgres sidecar on the shared network and makes `start_container` inject `BALE_POSTGRES_URL` for every container, each server scoped to its own database derived from its `data_root` (the metadata analogue of the S3 per-`data_root` bucket prefix). It composes with `--backend s3`; the only SQLite-specific phase, `failure-dbbusy`, self-skips under `--meta postgres`. Not run by `cargo test --workspace`. Read [`tests/e2e/README.md`](tests/e2e/README.md) — especially the **Design** section — before changing the harness, the bundled `Dockerfile`/`entrypoint.sh`, or any wire bit the test depends on (the resolver's scp-style URL parser, the JSON pointer shape, the `BALE_GRANTS` env format, the `/v1/usage` response shape, the `clean-cache` schema). Pure stdlib Python; runs on Linux/macOS/Windows hosts without pip. Phases that need xet's keyed-BLAKE3 hashes (to craft xorbs/shards) call the test-only `bale-e2e-tools` binary (`crates/bale-e2e-tools`, built with `cargo build --release -p bale-e2e-tools`), which uses the exact hashing/serialization code the server verifies with.
- **`crates/git-bale/src/mount/`** — two read-only FUSE mounts that share infrastructure: `git-bale mount-diff <revA> <revB>` (both sides of a diff, names labelled `name__<label>.ext`) and `git-bale mount <rev>` (single revision, original names). `mount-diff` populates its inode tree up front from the diff result; `mount <rev>` is *lazy* — directories carry an unresolved gix tree OID and read their children only when FUSE first looks inside, so mounting a 100k-file repo doesn't walk 100k tree objects at startup. Plain blobs stream from the ODB (cap 16 MiB), Bale pointers reconstruct via cache-first then network-fallback (same hot/cold path as the smudge filter). The userspace FS driver is dlopened at runtime via `libloading`, never linked, so the workspace builds without it — a `MountBackend` trait under `mount/backend/` selects one impl per target: **`libfuse.rs`** on unix (`libfuse.so.2` on Linux, `libfuse-t.dylib` on macOS — binding is libfuse 2.x because fuse-t advertises 2.9.9 and libfuse 3 silently mis-positions every op slot after `readlink`) and **`winfsp.rs`** on Windows (WinFsp's `winfsp-x64.dll` FUSE-compat layer, entry point `fsp_fuse_main_real`; its `fuse_operations` is a *different* layout from libfuse 2.x — `getdir` at slot 1, i64 `fuse_off_t`, WinFsp's own `fuse_stat`/`fuse_file_info`). The two share the backend-agnostic VFS/reader/diff and the path→node helpers (`cstr_to_path`/`lookup_path` in `backend/mod.rs`); `mount/mod.rs` reaches whichever compiled via the `PlatformBackend`/`ensure_available` aliases. A missing driver triggers a friendly install-hint exit before any other work. See `docs/ARCHITECTURE.md` § "`git-bale mount-diff` and `git-bale mount`" for tricky bits (path-based callbacks, OnceLock active-VFS, never-reconstruct `getattr`, lazy-dir population, per-open tempfile handles, the WinFsp ABI).

## Common commands

```bash
cargo build --workspace
cargo fmt --all
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings

# Behavior is verified end-to-end only — there are no Rust tests.
python3 tests/e2e/run.py               # full SSH push/clone/stash/gc harness (needs podman)
python3 tests/e2e/run.py --backend s3  # the same whole suite against an S3/MinIO blob store
python3 tests/e2e/run.py --meta postgres # the same whole suite against a Postgres metadata store
```

The pre-commit hook (`.pre-commit-config.yaml`) runs `cargo fmt --check` and the clippy command above with `-D warnings`. **Both must pass before declaring a code task done** — run them yourself, don't wait for the user's commit to find out.

Running the binary needs two hex secrets and either `BALE_GRANTS` (static dev authz) or `BALE_AUTHZ_HTTP_URL` (delegate to an upstream `/check_access`); see `README.md` "Quick start".

## Tests

There are **no Rust unit or integration tests** — behavior is verified purely from the user's perspective by the out-of-band end-to-end harness under `tests/e2e/`. `cargo test --workspace` builds clean but runs nothing. Prove behavior changes by extending the e2e harness, not by adding `#[cfg(test)]` modules.

- `tests/e2e/run.py` — full harness: bundles `baleforgit-server` + `openssh-server` in one podman container and drives the release `git-bale` binary through stage/unstage/stash/pop/commit/push/clone over real SSH, plus chunk-level dedup assertions and adversarial cases (wrong token, tampered xorb, quota exceeded, `upload-guards`, `shard-guards`, `xorb-layout-heal`, `global-dedup-hit`, `oversize-xorb`, `large-file`, `fetch-overlap`, `dedup-repeated-chunk`, `quota-atomic`, `canonical-scope`). `--backend s3` runs the same whole suite against a MinIO sidecar instead of the fs blob store; `--meta postgres` runs it against a Postgres sidecar instead of the SQLite `meta.db` (the two compose).
- `tests/e2e/baleharness/phases/local.py` — twenty-two no-server phases (group g3): `local-basic` (init-local → add/commit/checkout with no server), `local-gc-abandon` (staged then abandoned change is swept by gc), `local-shared-dedup` (two repos sharing `~/bale-local` dedup at the object level), `local-prune-shared` (`git-bale prune --shared` reclaims unreachable objects while preserving live ones), `local-clean-gc-race` (deterministic clean-vs-gc data-loss race, widened via `BALE_TEST_CLEAN_MARKER_DELAY_MS`), `local-cache-hit-gc-race` (same race via a clean-cache-HIT re-add, widened via `BALE_TEST_CLEAN_CACHE_HIT_DELAY_MS`), `local-concurrent-stress` (per-repo add+gc and shared add+prune under natural concurrency — no hang, no lost file), `local-gc-grace` (reclaim grace protects a young orphan marker and reclaims it once aged, via `BALE_GC_GRACE_SECS`), `local-stash-reflog` (content reachable only from `stash@{1}` survives gc and pops), `local-worktree-gc` (main's gc keeps a linked worktree's staged/committed content), `local-prune-cross-repo` (prune keeps content cleaned in B but referenced only by A), `local-tampered-store` (corrupt store content fails the checkout; no wrong bytes in the worktree), `local-autostash` (a conflicted `rebase --autostash` keeps the stashed bale content through gc and restores it), `local-prune-missing-repo` (content reached by a present repo survives `prune --shared --force` after the repo holding its only marker is deleted), `local-store-owner` (a second repo is refused a non-shared store; its gc never sweeps the owner's objects), `local-moved-shared-repo` (a moved shared repo re-registers on gc and keeps its content through `prune --force`), `local-reclone-same-path` (a repo re-cloned at the same path keeps its store's committed content through zero-marker and last-dead-marker gc), `local-in-gitdir-store-claim` (a store inside a repo's git dir is claimed via `.bale-owner` in both orders), `local-pointer-passthrough` (`add --renormalize` of raw pointer text keeps the pointer), `local-moved-repo` (a moved repo keeps its default store; a missing external store is refused, not recreated), `local-store-switch` (a clean-cache hit after switching stores, or after the store is wiped and re-created at the same path, re-cleans into the current store), `local-prune-force-moved` (after `prune --force` skipped a moved repo, a re-add there re-stages instead of hitting its stale clean-cache).
- `tests/e2e/s3lib.py` — two S3 phases (`phase_s3_basic`, `phase_s3_dedup`) that `--coverage` runs against the instrumented image; no standalone entry point (the whole suite on S3 is `run.py --backend s3`, and the server↔MinIO drop is the `failure-s3-conndrop` phase).
- `tests/e2e/run_matrix.py` — drives multiple harness configurations (`--s3` runs the whole suite on the S3 backend; `--postgres` on the Postgres metadata store; both flags compose).

Read [`tests/e2e/README.md`](tests/e2e/README.md) — especially the **Design** section — before changing the harness, the bundled `Dockerfile`/`entrypoint.sh`, or any wire bit the harness depends on (the resolver's scp-style URL parser, the JSON pointer shape, the `BALE_GRANTS` env format, the `/v1/usage` response shape, the `clean-cache` schema). Pure stdlib Python; runs on Linux/macOS/Windows hosts without pip. Phases that need xet's keyed-BLAKE3 hashes (to craft xorbs/shards) call the test-only `bale-e2e-tools` binary (`crates/bale-e2e-tools`, built with `cargo build --release -p bale-e2e-tools`), which uses the exact hashing/serialization code the server verifies with.

## Engineering guidelines

- **Comments earn their place.** Prefer self-explanatory code. Only add a comment for the non-obvious *why* — a hidden constraint, a workaround, a load-bearing invariant, an interaction with the wire protocol. No paragraphs, no docstrings that restate the function signature, no "this function does X" headers. Recent commits ("Trim comments a bit", "Optimize comments") deliberately deleted a lot of noise; don't reintroduce it.
- **Trim comments on every code change.** After writing or editing code, do a dedicated pass over the diff to simplify, trim, or remove comments and docstrings — *before* reporting the task done, not as a follow-up the user has to request. Drop function-shape docstrings, "what" comments that restate code, and section banners inside function bodies. Keep only *why* comments, and tighten the survivors (one line, name the actual failure mode in concrete terms).
- **Update the docs in the same change.** Any change that touches a trait signature, a wire endpoint, an env var, the storage schema, the auth flow, or a "Tricky bits" item must update `docs/ARCHITECTURE.md`, `docs/BALE_FORGE_PROTOCOL.md`, `README.md`, and/or this file as appropriate. Stale docs are worse than no docs.
- **Treat user data as load-bearing.** This system is a primary store for large binary artifacts — corruption is not recoverable from git history. Be paranoid about:
  - **Consistency** — writes that span the blob store and the metadata store must remain correct under partial failure. Prefer content-addressed idempotency (re-upload returns success) over locks. When persisting on the filesystem, write to `tmp/` then `rename(2)`. Never leave a half-written xorb or shard visible.
  - **Concurrency** — handlers are `async` and the router is shared across requests. Don't assume serialised access. Verify that two concurrent uploads of the same content, two concurrent reconstructions of the same file, or an upload racing a dedup query all converge to a consistent state.
  - **Security** — the per-repo scope check is load-bearing; don't relax it (404, not 403, on cross-repo probes). Signed transfer URLs must enforce the `Range` match and use constant-time signature compare. Never log JWTs, hub bearers, or signing keys. New endpoints default to *inside* the auth middleware; opting out is a deliberate decision that needs justification in the code.
- **Avoid crashes.** No `unwrap` / `expect` / `panic!` / `unreachable!` on inputs that can come from the network, the filesystem, env vars, or another process. Use `?` with a typed error (`CoreError`, `ApiError`, `anyhow::Error` at binary edges). `expect` is only acceptable for invariants the compiler can't prove but the surrounding code does — leave a one-line comment saying why it can't fail. A server crash kills every in-flight request; a returned error doesn't.

## Don't "fix" these without being asked

`/v1/reconstructions/*` must keep honoring `Range` (terms overlapping the range + `offset_into_first_range`, 416 past EOF): xet-data fetches every file over 2 × 256 MiB in Range blocks even when asked for `0..file_size`, and the old "always return the full file's terms" behavior made such files unclonable (the `large-file` e2e phase guards it). Don't remove it on the theory that the client's `0..file_size` cap avoids block fetches — it doesn't.

libfuse in `mount/backend/libfuse.rs` (and WinFsp in `mount/backend/winfsp.rs`) is loaded with `libloading` at runtime, not linked at build time. Don't switch either to `extern "C"` linkage or a `-sys`/SDK crate — that would force every developer to install the FS driver (libfuse / the WinFsp SDK) just to build the workspace, even if they never run a mount.
